# Directory / discovery data sources — findings, 2026-08-16

Sources are official documentation and published data files only. No protocol
implementation source was read; mrefd, urfd, ref-dash and ASL3-API repos turned
up in search results and were not opened (LP-1/LP-2).

## M17 — solved, and cleanly

**`https://m17-project.github.io/hostfiles/M17Hosts.json`** — the M17 Project's
own host file, served from their GitHub Pages. Generated 2026-08-15 22:32 UTC,
so it is live and maintained. 167 entries.

Top level: `_refcheck_metadata` + `reflectors` array.

Per M17 reflector entry:
`designator, name, slug, url, dns, ipv4, ipv6, modules, encrypted, port,
sponsor, country, ip_source, dns_cache_updated_at, last_verified_at,
network_type`

- Ports are mostly 17000, some 17001–17003.
- `dns` is often null; `ipv4` is the primary identifier. Mix of both.
- `modules` for M17 entries are single letters. URF entries (multiprotocol —
  DMR/P25/NXDN/YSF as well as M17) carry a richer `modules` array with
  per-module mode and transcode info; those need filtering to the M17 modules.
- `encrypted` is a per-reflector flag. FR-2.5 forbids an encryption UI, but
  displaying "this reflector carries encrypted traffic" is not encryption UI.
- `country` is a two-letter code, `sponsor` a callsign or org.

**Provenance and terms.** `_refcheck_metadata.license` reads: "Reflector data
provided by DVRef — https://dvref.com/aup/", processor "RefCheck.Radio Hostfile
Processor; Chip Cuccio - W0CHP". So the data is DVRef's, republished by the M17
Project. **The AUP could not be read: dvref.com returns 403 to automated
fetches** — as did their mrefd listing guide. That 403 is itself a signal about
automated consumption, though it may only be bot filtering rather than policy.
Worth opening https://dvref.com/aup/ in a browser before shipping a client that
fetches the list on a schedule. Consuming the M17 Project's copy rather than
hitting dvref.com directly is the politer path either way, and is what the file
appears to be published for.

## AllStarLink — available, and richer than expected

### Node number to address: public and unauthenticated

**`https://stats.allstarlink.org/api/stats/<node>`** returns JSON including
`ipaddr` (e.g. `"18.224.69.177"`), the port (4569), `callsign`, `Status`,
`keyed`, location and coordinates, uptime, a `linkedNodes` array carrying the
same fields for each linked node, and access-permission flags
(`telephoneportal`, `webtransceiver`).

That is exactly the node -> address resolution Currawong needs, with no
authentication. It is per-node rather than a bulk list, which suits a
"connect to node N" flow better than a browser anyway.

### Bulk metadata, no addresses

- `https://www.allstarlink.org/nodelist/` — searchable web list. Columns: Node,
  Owner, Callsign, Location, Frequency, CTCSS/DCS, Site, Affiliation, Last Seen
  UTC, **App Access Enabled**. No addresses, no documented export endpoint.
- `astdb.txt` is the file the dashboard ecosystem uses for node metadata
  (number, callsign, description, location). Downloaded nightly by node-side
  scripts. Metadata only — no addresses.
- `rpt_extnodes` (`/var/lib/asterisk/rpt_extnodes` on a node) is the real
  number->IP list, generated by the registration system and pulled by
  **registered nodes**. Not a public endpoint. The stats API makes it
  unnecessary for our purposes.

### The bigger finding: App Access is an official third-party path

`https://allstarlink.github.io/user-guide/externalapps/` documents a sanctioned
route for external applications, and names existing ones: RepeaterPhone (iOS),
Transceive (macOS), DVSwitch Mobile (Android), SharkRF M1KE, IAXRpt (legacy,
discouraged).

Four authentication mechanisms are described:

1. **Portal / Web Transceiver** — the app authenticates with the operator's
   *AllStarLink Portal account credentials*, and the node owner enables
   "App Access" per node. This is what the nodelist's "App Access Enabled"
   column reports.
2. **IAX direct** — username/password configured on the target node's
   `iax.conf`. **This is what Currawong does today.**
3. **SIP direct** — same idea over SIP.
4. **Node registration** — the app registers as its own node using portal
   credentials and a node password. Also already supported (IAX-8b).

Two things follow. First, the terms question that OQ-1 asked about EchoLink
looks materially easier here: AllStarLink documents third-party apps, names
them, and ships a per-node switch for admitting them. That is closer to an
invitation than a tolerance. Second, **Web Transceiver is a capability we do
not have** — nodes with App Access on but no IAX user context for us are
reachable by RepeaterPhone and not by Currawong. Whether that is worth
implementing is a maintainer call and a library-side task, not an app one; it
is also new protocol work with its own clean-room question, since the only
documentation found so far is a forum thread ("WebTransceiver Authentication
API"), not a specification.

## Status of the work

- **M17 chooser — done.** `M17HostFile`, `HostFileReflectorDirectory`,
  `ReflectorBrowser` and `ReflectorBrowserView`, in the Reflectors pane. See the
  README. The parser handles both entry shapes and filters URF modules to the
  ones an M17 client can use.
- **AllStarLink lookup — not started.** Not a browser but a *resolver*: the
  operator types a node number, the app asks the stats API for `ipaddr`, and the
  host field stops being something a human has to know. Should degrade to the
  manual host field when the lookup fails or the node is private. Would also
  give "is it keyed / who is it linked to" for free, later.
- **Open question for the maintainer — Web Transceiver.** Worth a plan row
  either way, even if the answer is "not now", so it is not rediscovered. Note
  it is library work and new protocol work, with its own clean-room question:
  the only documentation found is a forum thread, not a specification.
- **Open question for the maintainer — the DVRef AUP.** Unread, because
  dvref.com serves 403 to automated fetches. Worth opening in a browser before
  the app fetches the list on any kind of schedule.
